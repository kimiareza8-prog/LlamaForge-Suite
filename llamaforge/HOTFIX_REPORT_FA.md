# عیب‌یابی 0.34.3-hotfix

این نسخه ادامهٔ 0.34.2-diagnostics است. تمرکز این دور بر صحت لاگ قابل دانلود، لغو دسترسی در زمان اجرا و خطاهای اتصال/ارسال تلگرام بود. مشکل‌ها با ورودی مصنوعی و Client کنترل‌شده بازتولید شدند؛ حساب واقعی Telegram یا مدل GGUF روی Windows در این محیط اجرا نشده است. فایل‌ها و تصاویر خصوصی کاربر داخل انتشار نیستند.

## خطاهای واقعی و اصلاحات

| مشکل بازتولیدشده | رفتار اصلاح‌شده |
|---|---|
| دانلود حین پایان درخواست، رویدادهای قدیمی را با وضعیت جدید «کامل» ترکیب می‌کرد | رویداد و Metadata زیر قفل مشترک Snapshot می‌شوند؛ parsing و فشرده‌سازی پس از آزادکردن قفل انجام می‌شود. کامل‌بودن به رویداد پایانی معتبر، تعداد و پیوستگی رویدادها وابسته است |
| یک خط نیمه‌نوشتهٔ JSONL دانلود کل گزارش را خراب می‌کرد | رویدادهای سالم قابل دریافت‌اند؛ قسمت خراب در `read_errors` مشخص و گزارش ناقص علامت زده می‌شود |
| Metadata خراب یا حذف‌شده گزارش را مخفی یا فهرست را خراب می‌کرد | گزارش از فایل رویداد قابل بازیابی است؛ یک گزارش خراب مانع دیدن بقیه نمی‌شود |
| قطع اتصال یا Revoke ناموفق، وضعیت محلی حساب را متصل نگه می‌داشت | حساب در `finally` متوقف و مراجع/رسیدهای جاری پاک می‌شوند. حذف Vault فقط پس از تأیید خروج Telegram انجام می‌شود؛ خطا همچنان گزارش می‌شود |
| لغو از قبل ثبت‌شده ممکن بود بعد از ارسال RPC دیده شود | پیش از زمان‌بندی RPC بررسی می‌شود. لغو پس از شروع ارسال، تضمین عدم تحویل پیام نیست |
| FloodWait به «تحویل نامعلوم» تبدیل می‌شد و cooldown ثبت نمی‌شد | محدودیت اعلام‌شدهٔ Telegram به لایهٔ اجرا می‌رسد؛ تماس‌های بعدی تا پایان cooldown مسدودند |
| مدل با تغییر `request_key` می‌توانست همان پیام را دوباره ارسال کند | رسید بر اساس Turn واقعی، Workspace، نوع/شناسهٔ مخاطب، متن و مرجع پاسخ ساخته می‌شود؛ کلید مدل اختیاری است. پیام یکسان در درخواست تازهٔ کاربر قابل ارسال است |
| شکست درخواست کد ورود دوم، challenge شمارهٔ قبلی را باقی می‌گذاشت | challenge قبلی پیش از درخواست تازه پاک می‌شود؛ کد جدید با اطلاعات قبلی مصرف نمی‌شود |
| کلاینت بدون `request_id`، شناسهٔ متفاوت برای استریم و Cancel داشت | شناسهٔ تولیدشده به payload هم داده می‌شود. درخواست Bridge نیز شناسهٔ پایدار مبتنی بر اپ و پیام دارد |
| برداشتن تیک Permission حین اجرای Agent روی Snapshot قبلی اثر نداشت | Executor پیش از هر فراخوانی، مجوز ابتدایی و مجوز جاری را اشتراک می‌گیرد؛ مجوز لغوشده متوقف می‌شود و روشن‌شدن بعدی مجوز، درخواست قدیمی را گسترش نمی‌دهد |

لاگ ابزار هر دو وضعیت `requested_permissions` و `permissions` مؤثر را ثبت می‌کند. دسترسی Workspace، سایت و Telegram مستقل‌اند. خطای خواندن تنظیمات جاری، عملیات را مسدود می‌کند.

## تست‌های بازگشت

در `tests/test_diagnostics_hotfix.py` بیست مورد اضافه شد:

- ۷ مورد خروجی هم‌زمان، JSONL ناقص، چهار شکل Metadata خراب و فایل بدون Metadata.
- ۷ مورد قطع/Revoke ناموفق، لغو قبل از ارسال، cooldown، تغییر کلید ارسال در حالت موفق/نامطمئن و challenge قدیمی ورود.
- ۱ مورد یکسان‌بودن شناسهٔ HTTP در Stream و Cancel.
- ۵ مورد لغو مجوز Workspace/Website/Telegram read/Telegram write و جلوگیری از گسترش مجوز درخواست قبلی.

تست‌ها پیش از اصلاح نوشته و اجرا شدند. اجرای اول ۱۴ شکست را ثبت کرد؛ آزمون لغو مجوز ۴ شکست و ۱ موفقیت داشت. آزمون شناسهٔ HTTP ابتدا نبود شناسه در payload را نشان داد؛ Fixture آن یک متد جانبی ثبت خطا نداشت که پیش از اجرای سبز تکمیل شد. شواهد این مراحل در `audit/hotfix-*-red.txt` هستند.

| بررسی | نتیجه |
|---|---|
| Baseline همان 0.34.2 | ۴۰۰ موفق، ۱ اجرا‌نشده؛ ۴۹٫۷۳ ثانیه |
| Suite نهایی 0.34.3 | ۴۲۰ موفق، ۱ اجرا‌نشده؛ ۳۸٫۹۴ ثانیه |
| تست‌های هدفمند Agent/Telegram/Tracing | ۱۳۹ موفق |
| Tracing و Hotfix پس از اصلاح سربار | ۳۶ موفق |
| Node UI + protocol | ۱۹ موفق: ۱۸ مورد UI و یک فایل تست پروتکل |
| Syntax دو رابط JavaScript | موفق |
| `git diff --check` | موفق |

تست اجرا‌نشده به PHP CLI وابسته است که در این محیط نصب نیست. PHP و JavaScript این دور تغییر نکردند. بررسی بصری مرورگر و تست حساب واقعی Telegram انجام نشده‌اند؛ آزمون‌های UI مبتنی بر DOM مصنوعی‌اند. زمان Suite سرعت مدل را اندازه نمی‌گیرد.

## اندازه‌گیری قبل و بعد

Benchmark قبلی `scripts/benchmark_diagnostics.py` با سه جفت اجرای متناوب subprocess تکرار شد؛ هر اجرا ۳۵ درخواست، ۵ Warm-up، مدل مصنوعی و `tracemalloc` داشت. کد پایهٔ `request_tracing.py` از commit `c60aafd9e6e4413f8106c962c1b2f715b0b523f9` بارگذاری شد. جدول، میانهٔ سه اجرای هر نسخه را نشان می‌دهد؛ p95 نیز میانهٔ p95 همان اجراهاست.

| سربار ضبط مصنوعی | 0.34.2 | 0.34.3 |
|---|---:|---:|
| Median بدون ضبط | ۰٫۰۰۹ ms | ۰٫۰۰۹ ms |
| Median با ضبط | ۸٫۱۷۵ ms | ۵٫۳۷۴ ms |
| p95 با ضبط | ۹٫۷۸۲ ms | ۵٫۷۳۷ ms |
| Peak تخصیص Python، با ضبط | ۱۷۶٬۰۹۲ بایت | ۱۵۹٬۷۱۴ بایت |

اصلاح اولیهٔ بازیابی، هزینه را از ۸٫۰۱۲ به ۱۲٫۷۱۸ms رسانده بود. Profile نشان داد پاک‌سازی قدیمی‌ها دو بار در هر درخواست Metadata همهٔ گزارش‌ها را دوباره می‌خواند و redact می‌کرد. این مسیر به بررسی سن/حجم فایل تبدیل شد؛ پاک‌سازی Secret پیش از نوشتن و خواندن امن فهرست UI حفظ شده‌اند. نسخهٔ کندتر منتشر نشد. نتایج اولیه و نهایی در `audit/hotfix-diagnostics-before-optimization.json` و `audit/hotfix-diagnostics-benchmark.json` هستند.

کاهش نهایی حدود ۳۴٪ فقط برای سربار همین Fixture است. Peak بالا تخصیص Python است، نه RAM فرایند مدل. Prompt tok/s، Generation tok/s، TTFT واقعی مدل، Peak RAM/GPU و زمان Load در این دور اندازه‌گیری نشده‌اند؛ بهبود inference ادعا نمی‌شود.

## فایل‌های تغییرکرده

- `core/request_tracing.py`: Snapshot سازگار، بازیابی گزارش خراب و پاک‌سازی بر اساس سن/حجم.
- `core/telegram_skill.py`: هویت Turn، جلوگیری از ارسال تکراری و اصلاح چرخهٔ ورود/قطع/لغو/محدودیت نرخ.
- `core/agent_tools.py`: مجوز مؤثر هنگام اجرا و انتقال Turn به Telegram.
- `core/skill_contracts.py`: حذف اجباری‌بودن کلید ارسالِ مدل.
- `web/server.py`: اتصال به تنظیمات زنده، شناسهٔ پایدار Remote و شناسهٔ مشترک HTTP/Cancel.
- `tests/test_diagnostics_hotfix.py` جدید؛ انتظار نسخه در `tests/test_web_shell.py` به‌روز شد.
- فایل‌های `VERSION`، `__init__.py` و User-Agentهای `net.py`، `personal_brain.py` و `trainable_models.py` فقط برای هماهنگی نسخه به‌روز شدند.
- READMEها، CHANGELOG، راهنمای Skill/Telegram/Diagnostics و شواهد مصنوعی `audit/hotfix-*` به‌روز شدند.

## محدوده و مرحلهٔ بعد

رسید Telegram در حافظه است و پس از قطع اتصال/Restart باقی نمی‌ماند؛ exactly-once بین Restartها تضمین نمی‌شود. تغییر متن یا مخاطب، قصد ارسال متفاوت حساب می‌شود. در تحویل نامطمئن باید تاریخچهٔ همان گفت‌وگو بررسی شود؛ تکرار کورکورانه انجام نمی‌شود. لغو Permission یا Cancel، پیام خارجی از قبل تحویل‌شده را پس نمی‌گیرد.

اتصال واقعی، ورود دومرحله‌ای و Vault ویندوز هنوز باید روی دستگاه کاربر سنجیده شوند. درخت Skill جدیدی برای جمله‌های خاص ساخته نشده؛ Router و آموزش Brain در این دور بازنویسی نشدند. Adaptive، CPU/GPU/Hybrid/Max Both، Lazy mmproj و تنظیمات دستی Context تغییر نکردند. Bridge PHP، updater اتمیک، `owner_key`، `agent_token` و `data/config.php` تغییر نکرده‌اند. وابستگی جدیدی اضافه نشده است.

برای دو مشکل قدیمی تصویر تقویم و «پوشه + انتقال پیوست»، شواهد قبلی هنوز پارامتر/Observation کامل ندارند. پس از نصب این نسخه هر درخواست را جداگانه اجرا کنید و از Logs → Full request log، ZIP همان درخواست را بگیرید. این Trace برای تشخیص خطای مدل، تاریخ، مرجع فایل یا Sync لازم است؛ حل قطعی آن دو رفتار از روی تست‌های مصنوعی ادعا نمی‌شود.
