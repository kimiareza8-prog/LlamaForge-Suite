# Smart Skill Tree — نسخهٔ 0.34.0

مسیر اجرا:

`Intent → Family → Shortlist → Typed operation → Execute → Observation → Re-plan / Verify → Stream`

## انتخاب بر اساس هدف

مدل تصمیم‌گیرندهٔ اصلی است. Router در یک پاسخ JSON هم Direct/Skills و هم Family را مشخص می‌کند. اگر مدل قدیمی فقط route بدهد، مرحلهٔ جداگانهٔ انتخاب Family همچنان کار می‌کند. برای سلام‌های ساده مرحلهٔ Router حذف می‌شود و فقط پاسخ واقعی مدل تولید می‌شود.

Guardها برای زمان واقعی، فایل پیوست، URL و درخواست عملیاتی واضح هستند. صرف وجود کلماتی مثل meeting، tomorrow یا browser در یک جملهٔ خبری، ترجمه یا توضیح نباید تصمیم معتبر Direct مدل را تغییر دهد. این Guardها محدود و قطعی‌اند؛ ادعای درک معنایی کامل برای هر عبارت ندارند. مدل می‌تواند خانواده‌های دیگری را اضافه کند.

ابتدا Family انتخاب می‌شود؛ سپس امتیاز واژه‌ها فقط داخل همان شاخه برای مرتب‌کردن ابزارها به کار می‌رود. سقف Shortlist با Context تنظیم می‌شود. کاتالوگ هر درخواست یک بار ساخته می‌شود. همهٔ Skillها داخل Prompt ریخته نمی‌شوند. اگر Observation به ابزار نصب‌شده‌ای بیرون از Shortlist نیاز داشته باشد، شاخهٔ آن باز و برنامه دوباره با Schema واقعی ساخته می‌شود.

## درخت قابلیت‌ها

| خانواده | عملیات عمومی |
|---|---|
| Time / Calendar | now، convert، month، list، create، update، cancel، delete |
| Files / Workspace | metadata، probe، list، search، read_content، store_attachment، write_text، replace_text، mkdir، move، rename، trash، restore، delete |
| Web | خواندن URL، بررسی دسترسی، جستجو، یافتن متن و دانلود |
| Browser | مشاهده و جابه‌جایی نشست؛ کلیک، تایپ و انتخاب با مجوز Website Write |
| API | HTTP با مجوز متناسب با method |
| Extensions | عملیات OpenAPI و Skillهای JSON نصب‌شده |

UI عملیات هر ابزار و مجوز خواندن/نوشتن آن را نمایش می‌دهد. برای «وقت خالی پیدا کن»، «پوشهٔ مستندات بساز» یا هر جملهٔ تازه Skill جدید ساخته نمی‌شود؛ مدل همین عملیات را ترکیب می‌کند.

## قرارداد ابزار

`skill_contracts.py` شامل `OperationPolicy` تایپ‌شده، Input Schema، Output Schema، پیش‌نیازهای هر عملیات، Side Effect، مجوز، Parallel Safety، Idempotence، Timeout، Retry، Network، هزینهٔ نسبی و روش Verify است. Metadata کامل در کاتالوگ و نسخهٔ فشردهٔ Schema در Prompt قرار می‌گیرد. HTTP method از تعریف ساختاریافته خوانده می‌شود، نه از توضیح آزاد ابزار.

Validator زیرمجموعهٔ Schemaهای استفاده‌شده در ابزارهای داخلی را بررسی می‌کند؛ پیاده‌سازی کامل استاندارد JSON Schema نیست. Calendar create به عنوان و تاریخ/زمان نیاز دارد؛ read_content به id یا attachment_id؛ store_attachment به attachment_id. مقدار نامعتبر operation پیش از اجرا به مدل برمی‌گردد.

نمونهٔ قرار فردا:

```json
{"operation":"create","title":"جلسه","relative_date":"tomorrow","time":"10:00"}
```

نمونهٔ تاریخ شمسی با سال مشخص:

```json
{"operation":"create","title":"جلسه","jalali":"1405-07-02","time":"10:00"}
```

برای «۲ مهر» بدون سال، مدل باید از now و زمینهٔ گفتگو استفاده کند یا ابهام لازم را روشن کند. ساعت تنها، تاریخ کامل فرض نمی‌شود.

## فایل‌ها

قاعده: دریافت → Metadata / Probe → تصمیم دربارهٔ هدف → خواندن فقط در صورت نیاز.

هر پسوندی در سقف حجم قابل دریافت است. Metadata شامل نام، پسوند، MIME، اندازه، SHA256 و Attachment ID است. دریافت همان محتوا با همان نام در یک Workspace رسید قبلی را برمی‌گرداند. پس از store_attachment و rename/move نیز رسید معتبر می‌ماند؛ UI شناسه را در تاریخچه ذخیره می‌کند.

- متن، Markdown، JSON/YAML/XML و کد: خواندن محدود به بودجهٔ متن.
- ZIP/TAR: فهرست امن؛ بدون Extract خودکار؛ مسیر خطرناک، symlink/hardlink، حجم و نسبت فشرده‌سازی نامعتبر مسدود می‌شود. `members` برای خواندن انتخابی است. خواندن مستقیم بدون members برای سازگاری، Preview محدود تولید می‌کند.
- DOCX/PPTX: استخراج متن XML محدود؛ XLSX: سلول‌ها با حل sharedStrings و ترتیب سلولی، بدون محاسبهٔ دوبارهٔ فرمول یا حفظ قالب‌بندی.
- PDF: نیازمند pypdf برای استخراج؛ دریافت و Metadata مستقل از نصب Parser است.
- عکس: Vision فقط پس از خواندن صریح محتوا؛ صرف ذخیرهٔ عکس mmproj را فعال نمی‌کند.
- Audio/Video/Binary/فرمت ناشناخته و آرشیوهای پشتیبانی‌نشده: دریافت و Metadata برقرار است؛ استخراج اختصاصی تضمین نمی‌شود.

نبود Parser یعنی «فایل دریافت شده ولی استخراج این نوع محتوا در دسترس نیست»، نه «به فایل دسترسی ندارم».

## مجوز، موازی‌سازی و بازیابی

Local Workspace Write مستقل از External Website Write است؛ حتی دانلود نیز نوشتن محلی محسوب می‌شود. کل نشست Browser سری اجرا می‌شود، چون navigation/snapshot نیز به وضعیت مشترک نشست وابسته‌اند.

۲ تا ۳ خواندن مستقل از یک Runtime و مدل Loadشده استفاده می‌کنند. Scope صاحب Workspace به Threadها منتقل می‌شود. Writeها موازی نمی‌شوند. Cancel دیگر منتظر join تمام خواندن‌های شبکه نمی‌ماند؛ I/O در حال اجرای Thread تا Timeout خودش ممکن است ادامه یابد.

فراخوانی شکست‌خوردهٔ یکسان، شامل خطای Preflight، مسدود می‌شود. رسید نوشتن موفق در همان Turn برای فراخوانی یکسان دوباره استفاده می‌شود. این تضمین exactly-once بین Restartها یا Turnهای مختلف نیست. نوشتن‌های محلی پس از اجرا از روی ID/وضعیت ذخیره‌شده بررسی می‌شوند؛ Verify عملیات خارجی همچنان به read/snapshot و قابلیت سرویس وابسته است.

## پاسخ و محدودیت‌ها

Planner JSON کامل دریافت می‌شود و سپس اجرا می‌شود. پاسخ نهایی در مسیر عادی، خطای Planner و پایان بودجه از Stream واقعی مدل می‌آید. خطای Stream و قطع بدون Final marker موفقیت فرض نمی‌شوند. API محلی SSE دارای replay محدود، شمارهٔ رویداد و Long-poll است؛ این replay مربوط به وضعیت برنامه است و Resume کامل پاسخ POST چت نیست.

دقت مدل 4B/7B روی همهٔ جمله‌های فارسی بدون اجرای مدل واقعی قابل تضمین نیست. تست‌های این نسخه از مدل کنترل‌شده برای بررسی تصمیمات، قراردادها و مسیرهای خطا استفاده می‌کنند. اندازه‌گیری سخت‌افزاری و موارد باقی‌مانده در AUDIT_REPORT_FA.md آمده است.

## اصلاح زمان قرار در 0.34.1

همان عملیات عمومی `calendar.update` می‌تواند `time`، `jalali`، `gregorian`، `relative_date` یا `start` کامل بگیرد. تغییر تاریخ به‌تنهایی ساعت قبلی را حفظ می‌کند؛ تغییر ساعت به‌تنهایی روز قبلی را نگه می‌دارد. اگر `end` نفرستید، مدت قرار قبلی حفظ می‌شود. رشتهٔ تاریخ/ساعت خالی خطاست و رویداد قبلی را تغییر نمی‌دهد. برای ساخت رویداد تمام‌روز با تاریخ شروع، پایان پیش‌فرض یک روز بعد است. Skill جدیدی مخصوص این جمله‌ها ساخته نشده است.
