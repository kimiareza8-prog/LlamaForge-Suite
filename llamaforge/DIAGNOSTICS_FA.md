# راهنمای لاگ کامل و Telegram — به‌روز برای 0.34.3

لاگ کامل و Telegram در **0.34.2-diagnostics** بر پایهٔ **0.34.1-stability** اضافه شدند؛ اصلاحات تکمیلی 0.34.3 در [HOTFIX_REPORT_FA.md](HOTFIX_REPORT_FA.md) آمده است. تمام لاگ‌ها و تصاویر ارسالی این دور متعلق به 0.34.1 هستند؛ شواهد آن‌ها به‌عنوان نتیجهٔ اجرای نسخهٔ جدید معرفی نمی‌شوند. فایل‌های شخصی ارسالی، اطلاعات ورود و Session تلگرام در مخزن و ZIP انتشار قرار نگرفته‌اند.

## استفاده از لاگ کامل

1. نسخهٔ جدید LlamaForge را اجرا کنید و در رابط **محلی** وارد **Logs → Full request log** شوید. ضبط به‌صورت پیش‌فرض روشن است و می‌توان آن را خاموش کرد.
2. درخواست مشکل‌دار را در چت محلی یا سایت متصل دوباره اجرا کنید. فعالیت سایت شناسهٔ `trace_…` را نشان می‌دهد؛ گزارش با شناسهٔ پیام سایت نیز قابل تطبیق است.
3. در Logs، فهرست درخواست‌ها را Refresh کنید، درخواست را انتخاب کنید و **Download full log ZIP** را بزنید. برای هر مورد مشکل‌دار، ZIP همان درخواست را بفرستید.

ZIP شامل `events.jsonl` برای بررسی ماشینی، `report.md` برای خواندن مستقیم، و `manifest.json` برای وضعیت و کامل‌بودن ضبط است. بازکردن هر رویداد در UI فقط جزئیات همان رویداد را می‌گیرد. **Copy system diagnostic** همچنان گزارش عمومی سیستم است؛ جایگزین ZIP درخواست نیست.

لاگ‌های قدیمی ورودی و خروجی کامل مدل را نداشته‌اند؛ این اطلاعات از گذشته قابل بازیابی نیست. دانلود گزارش در میانهٔ اجرا، قطع برنامه، پرشدن سقف ضبط یا خطای دیسک صریحاً گزارش را ناقص علامت می‌زند. از 0.34.3، داده و وضعیت از یک Snapshot سازگار گرفته می‌شوند؛ JSONL نیمه‌نوشته یا Metadata خراب/گمشده مانع بازیابی رویدادهای سالم نیست. جزئیات حذف‌شده در `manifest.read_errors` و گزارش خوانا ثبت می‌شوند.

## چه چیزی ضبط می‌شود؟

| مرحله | اطلاعات ثبت‌شده |
|---|---|

| آماده‌سازی | پیام قبل و بعد از آماده‌سازی Context، محدودیت‌ها و تنظیمات مؤثر Runtime |

| Skill discovery | کاتالوگ قراردادها، شاخه‌ها، Shortlist و Manifest واقعیِ فرستاده‌شده به مدل |
| هر نوبت مدل | شناسهٔ call، payload واقعی HTTP و fallbackهای سازگاری، خروجی خام و زمان اجرا |
| هر ابزار | شناسه، Operation، آرگومان، Permission، اعتبارسنجی، نتیجه/خطا، رسید و Verification موجود |
| Observation | نتیجهٔ کامل ابزار و نسخهٔ خلاصه‌شده‌ای که واقعاً به مدل رسیده است |
| پایان | پاسخ نهایی، وضعیت توقف/خطا/لغو، تعداد Delta، TTFT و usage/timings در صورت ارائهٔ Runtime |
| Web Bridge | کشیدن/فرستادن Workspace، خطای sync، اجرای مدل و تحویل پاسخ زیر یک Trace |

Reasoning یا تصمیم خیالی تولید نمی‌شود؛ فقط خروجی قابل مشاهدهٔ مدل و تصمیم‌های واقعی برنامه ثبت می‌شوند. استریم همچنان زنده به کاربر می‌رسد. برای جلوگیری از نشت Secret شکسته‌شده میان Deltaها، متن خروجی هنگام ذخیره به هم متصل و سپس پاک‌سازی می‌شود.

اطلاعات Runtime شامل وضعیت زنده و انتهای ۲۵۰ خط لاگ مشترک Runtime است؛ این قسمت ممکن است اطلاعات درخواست هم‌زمان دیگری را هم داشته باشد و اختصاصی یک درخواست نیست. آموزش Brain همچنان لاگ جلسهٔ Trainer جداگانه دارد؛ Full request log جایگزین همهٔ لاگ‌های آموزش نشده است.

## روند Agent و درخت اسکیل

وقتی Agent روشن است، Router ابتدا فقط عنوان و توضیح کوتاه خانواده‌ها را می‌بیند. در یک پاسخ JSON می‌گوید ابزار لازم است یا نه و، در صورت نیاز، خانواده‌های لازم را مشخص می‌کند. ترکیب این دو تصمیم یک فراخوانی اضافی را حذف می‌کند.

- **Direct:** پیام‌های آمادهٔ مکالمه مستقیماً به مسیر پاسخ و استریم می‌روند؛ Planner، کاتالوگ ابزار و حلقهٔ Agent ساخته نمی‌شود. سلام ساده حتی فراخوانی Router هم ندارد.
- **Skills:** فقط شاخه‌های انتخاب‌شده باز می‌شوند؛ Shortlist محدود و Schema عملیات همان شاخه‌ها به Planner می‌رسد. سپس اعتبارسنجی، اجرا، Observation و ادامهٔ برنامه یا پاسخ نهایی انجام می‌شود.
- Guard تنها قابلیت واضح را حفظ می‌کند. اکنون خانواده‌ای که Guard بازیابی کرده یا مدل در پاسخ اصلاحی داده است، دوباره از مدل پرسیده نمی‌شود.
- اسکیل‌های عمومی Web، Files، Calendar، Browser، API، Connectors، Custom و **Telegram** وجود دارند؛ برای هر جمله اسکیل تازه ساخته نشده است.

در Profile **Telegram only**، تنها Schema تلگرام قابل انتخاب است و Executor نیز فراخوانی خانواده‌های دیگر را رد می‌کند. چت Direct همچنان قابل استفاده است.

## دسترسی‌ها

در نصب تازه، مجوزهای Workspace، نوشتن سایت، شبکهٔ خصوصی و خواندن/ارسال تلگرام روشن‌اند. نصب بسته به‌تنهایی حساب یا سایت جدیدی را متصل نمی‌کند. تنظیمات ذخیره‌شدهٔ نسخهٔ قبلی، از جمله `false`های قبلی، حفظ می‌شوند. برای روشن‌کردن همه در نصب قبلی: **Agent → Enable all permissions → Save Agent settings**.

خاموش‌کردن هر تیک و Save هم ذخیره و پس از راه‌اندازی دوباره بازیابی می‌شود. از 0.34.3، فراخوانی‌های بعدی Agent در همان درخواست نیز لغو مجوز را رعایت می‌کنند؛ این کار عملیات خارجی از قبل شروع‌شده را برنمی‌گرداند. نوشتن محلی، نوشتن سایت و ارسال تلگرام سه Permission مستقل هستند. خاموش‌بودن نوشتن سایت جلوی ساخت رویداد یا ذخیرهٔ فایل را نمی‌گیرد.

ریشهٔ خطای UI این بود که Refresh وضعیت صفحهٔ Agent را دوباره می‌ساخت و تغییر ذخیره‌نشده را از بین می‌برد. فرم اکنون Draft نگه می‌دارد؛ اگر حین Save ویرایش تازه‌ای انجام شود، پاسخ درخواست قبلی آن را پاک نمی‌کند. backend نیز مقدار رشته‌ای مانند `"false"` را به‌جای Boolean نمی‌پذیرد.

## Telegram حساب شخصی

در صفحهٔ Agent کارت **Telegram** را باز کنید:

1. **Install Telegram support**، وابستگی اختیاری `Telethon==1.45.0` و `keyring>=25.6,<26` را نصب می‌کند.
2. API ID و API Hash را از `my.telegram.org` در همان کارت وارد کنید؛ شماره باید همراه کد کشور باشد. **Send login code** را بزنید.
3. کد Telegram را وارد کنید؛ در صورت درخواست، رمز دومرحله‌ای را هم در همین UI وارد کنید. **Verify login** را بزنید.
4. **Disconnect** اتصال جاری را قطع می‌کند؛ **Resume saved session** از Vault دوباره وصل می‌شود. **Revoke session** در صورت تأیید Telegram، خروج و حذف Session ذخیره‌شده را انجام می‌دهد. حتی با خطای شبکه، حساب محلی متوقف می‌ماند؛ اگر خروج تأیید نشده باشد Session در Vault برای تلاش دوباره حفظ می‌شود.

Credentialها فقط در Vault سیستم‌عامل نگهداری می‌شوند؛ fallback متنی برای Session وجود ندارد. backend امن لازم است: Windows Credential Manager، macOS Keychain، Secret Service یا KWallet. API Hash، کد ورود، رمز و Session ورودیِ اسکیل مدل نیستند. آن‌ها را داخل چت نفرستید.

| شاخه | عملیات قابل استفاده |
|---|---|
| حساب | `status` |
| گفت‌وگوها و مخاطب | `recent_chats`، `resolve_person` |
| Context انتخاب‌شده | `messages`، `my_messages`، `search` |
| پیام‌رسانی | `send`، `reply` |

مثال: «پیام‌های اخیر علی در تلگرام را بخوان» یا «در تلگرام به @username بگو فردا ساعت ۹ می‌رسم». ارسال در تست‌ها انجام نمی‌شود؛ اتصال واقعی و درخواست خود کاربر لازم است.

جستجوی نام فقط مشخصات حداکثر ۱۰۰ گفت‌وگوی اخیر را بررسی می‌کند؛ username دقیق هم قابل Resolve است. نام‌های مشابه بدون مرجع قابل ارسال برگردانده می‌شوند تا مدل از کاربر رفع ابهام بخواهد. فهرست اخیر به‌تنهایی مجوز ارسال به مخاطب را نمی‌دهد؛ `resolve_person` یکتا لازم است. مراجع به Workspace درخواست تعلق دارند و پس از ۱۵ دقیقه منقضی می‌شوند.

خواندن پیش‌فرض ۵ پیام، سقف ۱۵ پیام و حداکثر ۱۰هزار کاراکتر متن از همان گفت‌وگو دارد. محتوای رسانه خودکار دانلود نمی‌شود. ارسال متن ساده با شناسهٔ واقعی درخواست، رسید ID و خواندن مجدد پیام انجام می‌شود. `request_key` اختیاری است؛ عوض‌کردن آن توسط مدل در همان درخواست باعث ارسال دوبارهٔ همان پیام نمی‌شود. درخواست تازهٔ کاربر می‌تواند تکرار عمدی پیام باشد. رسید نامطمئن اجازهٔ retry کورکورانه ندارد؛ رسیدهای این لایه در حافظه و تا قطع اتصال معتبرند. پس از قطع برنامه نیز برای ارسال نامطمئن باید وضعیت گفت‌وگو بررسی شود.

یک Client و Event loop مشترک استفاده می‌شود. عملیات محدودیت زمان و لغو دارند؛ نوشتن‌ها سریالی‌اند. مدل دیگری در RAM بارگذاری نمی‌شود. APIهای حساب از رابط محلی مدیریت می‌شوند؛ درخواست‌های Agent اپ‌های متصل هم تابع همان Permissionهای حساب پیکربندی‌شده هستند.

برای این نسخه یک Adapter مستقیم و کوچک Telethon انتخاب شد تا قراردادهای محدود، لغو و بودجهٔ Context قابل تست باشند. طرح پیوست شامل پیشنهادهای گسترده‌تری بود: MCP daemon، QR login، Auto Reply/Autopilot، دانلود/ارسال رسانه و مدیریت گروه در این نسخه پیاده‌سازی نشده‌اند. هیچ listener یا پاسخ خودکاری هنگام اتصال حساب شروع نمی‌شود.

مراجع پیاده‌سازی: [Telethon Client](https://docs.telethon.dev/en/stable/modules/client.html)، [Session storage](https://docs.telethon.dev/en/stable/concepts/sessions.html)، [keyring](https://keyring.readthedocs.io/en/latest/).

## خطاهای اثبات‌شده و تغییرات

| مشکل | اصلاح و محدودهٔ نتیجه |
|---|---|
| PHP فهرست خالی `items` را `[]` فرستاده و sync شکست خورده | فقط فهرست خالی به `{}` تبدیل می‌شود؛ دادهٔ نامعتبر همچنان رد می‌شود |
| فایل snapshot نامعتبر، تقویم را پیش از خطا تغییر می‌داد | اعتبارسنجی/اعمال فایل پیش از جایگزینی تقویم؛ تراکنش کامل چندفایلی ادعا نمی‌شود |
| لغو Remote task در callback بلعیده می‌شد | استثنای لغو منتقل و Event توقف به جریان مدل رسانده می‌شود |
| شمارنده‌های token و برخی متن‌های خطا بیش‌ازحد مخفی می‌شدند | Redaction، Metric و کلیدهای Credential را تفکیک می‌کند |
| Windows با Intel display GPU به‌اشتباه مسیر CPU ناسازگار را آماده می‌دانست | Doctor از CUDA/MPS واقعی Trainer استفاده کرده و checkpoint از قبل quantized را روی Windows CPU زودتر رد می‌کند |
| `tokenizer_config.json` به‌تنهایی آماده‌بودن Tokenizer حساب می‌شد | Doctor فایل واقعی Tokenizer/vocabulary را مطالبه می‌کند؛ سازگاری کامل Tokenizer باید روی نصب کاربر بررسی شود |
| نصب مجدد Runtime قبلی را پیش از موفقیت rename حذف می‌کرد | build جدید در مسیر یکتا نصب و pointer اتمیک عوض می‌شود؛ خطای rename قبلی را حذف نمی‌کند |
| تیک‌های Agent با Refresh برمی‌گشتند | Draft و حفظ ویرایش جدید حین Save |
| خانوادهٔ Router پس از Guard یا repair گم می‌شد | نگه‌داشتن خانواده و حذف استنتاج تکراری |

خطای Windows `Access is denied` ممکن است از مجوز پوشه یا آنتی‌ویروس هم باشد؛ نسخهٔ جدید حفاظت از build قبلی را تضمین می‌کند، حذف هر علت سیستم‌عاملی ادعا نشده است.

در لاگ آموزش LFM2، خطای بارگذاری Tokenizer ثبت شده است؛ این خطا OOM گزارش نشده. در لاگ Gemma قبلی هم checkpoint از قبل 4-bit با مسیر CPU ناسازگار بوده است. Full RAM که به‌دلیل بودجهٔ ناکافی رد شده، رفتار حفاظتی دارد و این حفاظت حذف نشده است.

دو تصویر تقویم و پوشه پارامتر ابزار و Observation کامل ندارند. نمی‌توان ادعا کرد علت دقیق پاسخ «رویداد قدیمی» یا انجام فقط بخش ساخت پوشه، قطعی حل شده است. نسخهٔ جدید اطلاعات لازم برای بازتولید همین دو مورد را ثبت می‌کند.

## نتایج نسخهٔ 0.34.2؛ نتایج جدید در HOTFIX_REPORT_FA.md

- مبنای 0.34.1: **352 passed, 1 skipped** در 63.85 ثانیه.
- نسخهٔ نهایی این دور: **400 passed, 1 skipped** در 41.49 ثانیه؛ ۴۸ مورد pytest اضافه شده است.
- تست UI با Node: **18 passed**، شامل ۴ مورد جدید لاگ و حفظ دسترسی‌ها. زمان Suite معیار سرعت مدل نیست.

Regressionها پیش از اصلاح برای UI دسترسی‌ها، Route repair/guard، snapshot خالی/نامعتبر، Remote cancel، Credential redaction، Runtime promotion و Tokenizer metadata ثبت شدند. تست‌های تلگرام با Client و Vault مصنوعی، بدون حساب یا پیام واقعی اجرا می‌شوند.

## نگهداری و محدودیت‌ها

لاگ محلی در `%USERPROFILE%/.llamaforge/logs/requests` قرار دارد؛ سقف عادی ۱۰۰ درخواست، ۲۵۶MiB مجموع فایل‌های رویداد/Metadata و ۳۲MiB هر درخواست است. از 0.34.3، حذف قدیمی‌ها بر اساس آخرین تغییر فایل و حجم انجام می‌شود و متن گزارش برای این کار بازخوانی نمی‌شود. درخواست در حال اجرا برای پاک‌سازی قدیمی‌ها حذف نمی‌شود؛ در چند اجرای هم‌زمان ممکن است سقف کلی موقتاً رد شود. محتوای باینری با Metadata/Hash جایگزین می‌شود، نه کپی مجدد فایل. Hashِ دادهٔ base64 در این لاگ مربوط به نمایش encoded آن است.

Credentialهای شناخته‌شده قبل از نوشتن حذف می‌شوند. با این حال لاگ کامل عمداً متن کاربر، فایل خوانده‌شده و پیام تلگرام را دارد؛ هر متن محرمانهٔ بدون برچسب قابل تشخیص خودکار نیست. ارسال ZIP دستی است و آپلود خودکار انجام نمی‌شود.

اتصال واقعی Telegram، ورود دومرحله‌ای و Vault روی Windows کاربر باید آزمایش شوند؛ تست مصنوعی جای آن‌ها را نمی‌گیرد. قابلیت‌های برنامه روی مدل کوچک به کیفیت خروجی همان مدل نیز وابسته‌اند. حفاظت از نام مخاطب مبهم و Permissionها در Runtime اجرا می‌شود و به تصمیم مدل واگذار نشده است.

Bridge PHP، `owner_key`، `agent_token`، `data/config.php` و updater آن تغییر نکرده‌اند. روش‌های CPU/GPU/Hybrid/Max Both، Adaptive، Lazy mmproj و تنظیمات ذخیره‌شدهٔ Context حفظ شده‌اند. Autotune، speculative decoding و آموزش LoRA در این دور بازنویسی نشده‌اند؛ بهبود عددی بدون Benchmark واقعی ادعا نمی‌شود.

## فایل‌ها و مرحلهٔ بعد

هستهٔ تغییرات: `request_tracing.py` و `telegram_skill.py` جدید؛ `agent_engine.py`، `agent_tools.py`، `skill_system.py`، `skill_contracts.py`، `config.py`، `redaction.py`، `net.py`، `remote_apps.py`، `workspace.py`، `runtime.py`، `personal_brain.py`؛ API و UI در `web/server.py`، `web/static/app.js` و `macos.css`. چهار فایل تست Python، تست‌های UI، اسکریپت Benchmark و مستندات اضافه یا به‌روز شده‌اند؛ User-Agent و شمارهٔ نسخه نیز هماهنگ شدند.

مرحلهٔ بعد: پس از نصب، درخواست «ساخت پوشه و انتقال همان پیوست» و «جلسهٔ ۶ مهر ساعت ۱۰» را هرکدام یک بار تکرار کنید و ZIP کامل هر درخواست را بگیرید. آن Trace مشخص می‌کند خطا در فهم هدف، انتخاب Operation، آرگومان تاریخ/فایل، sync، اجرا یا پاسخ نهایی رخ داده است. برای توسعهٔ بیشتر تلگرام، ابتدا ورود و یک خواندن محدود روی دستگاه واقعی سنجیده شود و بعد سراغ Auto Reply با محدودهٔ مخاطب مشخص برویم.
